# Making the trace store readable, navigable, and safe to build a service on

Date: 2026-08-28 · Status: implemented across the releases whose CHANGELOG
entries cite this file.

## What was asked

The owner is building a separate analysis service over `evals/traces/` — MCP or
direct reads, not yet decided — and asked three things: how the files are named
and whether that helps a human; why JSON rather than Markdown or XML; and
whether a clear, auto-updating dictionary can exist.

## What measuring found

* **273 tracked files, flat, named `t-<12 hex>.json`** — uuid4-derived, unsorted,
  meaningless. The directory listing tells a reader nothing.
* **Only 91 of the 273 are records.** 182 are build traces pytest leaked into the
  tracked store before 2026-08-26, set aside by `trace_store.suite_artifact()` —
  a rule that lived only in code and in CHANGELOG prose. **A service reading the
  directory gets a denominator three times too large**, which is not
  hypothetical: `ledger.py` once reported "4 of 251 build(s)" over a store
  holding seventeen.
* **No dictionary of any kind.** Every field's meaning lives in a comment inside
  `scripts/lib/trace_schema.py`. `evals/README.md` is 31 lines and never says
  the word "trace".
* **No recorded decision about the format.** 0.1.462's entry argues verdict
  provenance and a closed schema, never serialization.
* **`evals/` is development-side**, so traces never reach the published
  projection. The service reads the development repository.

Two robustness defects surfaced while measuring, neither of which had fired:

* **Writes were not atomic** — a bare `write_text` on a path that every phase
  stop and every close rewrites. A crash truncates the file and
  `trace_store.load()` swallows the `JSONDecodeError` and skips it, so the loss
  and the absence print the same thing.
* **Ids were never checked against the store.** 48 bits, and `_save` overwrites
  whatever is at the path it builds.

## What was decided, and what was declined

**JSON stays.** A trace is a machine-written record with exact types — `null` is
not `""`, an int is not a string — and three nested verdict maps holding
seventy-seven entries. Markdown needs a parser and loses the types; XML costs
more bytes for the same thing. The readability problem is real and is a
NAVIGATION AND DOCUMENTATION problem, so that is where it is fixed.

**Verdicts stay machine-only.** `trace.py` has no `--gate/--verdict/--pass` flag
by design, the same discipline `check_evidence.py` enforces one layer up. The
owner asked for hand-editable fields; the answer is one field, `annotations`,
holding a note and a set of tags — the two things a person is the AUTHORITY on.
Everything else is a measurement, and hand-editing a measurement is not an edit.

**The English-only red line is relaxed for that one field, deliberately.**
`check_repo`'s english-only guard already excluded `evals/traces/`, and its
stated reason — "a closed schema with nowhere to put prose" — stopped being true
the moment `annotations` gave it somewhere. The reason is now narrower: `evals/`
is development-side, so no trace reaches a reader of the published package, and
an operator's note about their own run is neither rule prose nor rule data.

## The shape

| artifact | reader |
|---|---|
| `evals/traces/README.md` | a person opening the directory for the first time: the store's two counts, what the gap between them is, and every field with its type, population, editability, fill rate and a `file:line` back into the schema |
| `evals/traces/index.jsonl` | one line per trace, summary fields only, ordered by `opened_at` — for a query, a script, or the service. `suite_artifact` is a COLUMN, so the filter travels with the data |

Both generated by `scripts/build/build_trace_dictionary.py`, `--check` in CI,
following the pattern this repository already uses five times. Adding the CI
step enrols the artifacts in release-time regeneration automatically:
`release.py` discovers generators by parsing `ci.yml`.

**The field meanings are cited, never copied.** The dictionary carries a
`trace_schema.py:<line>` per field and no restatement of the comment there — a
second copy of thirty descriptions is the drift this repository has fixed
twenty-six times, and it would be the first thing to rot.

## Still open

Date partitioning (`evals/traces/YYYY-MM/`) was approved and is not done. It
needs one resolver in `trace_store`, four production globs, and a migration —
and its risk is `check_deliverable.py`, which gates a deliverable on its trace
existing and distinguishes *no trace* from a *dangling id*. Both branches need a
test through the resolver before it lands.
